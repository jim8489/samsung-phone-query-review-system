# Architecture and design notes

## Request flow

1. FastAPI validates requests and exposes catalogue, comparison, chat, review and scraper routes.
2. SQLAlchemy stores phones, normalized specification rows, dated price observations, and chat history. SQLite is the default; PostgreSQL works through `DATABASE_URL`.
3. `GSMArenaScraper` searches GSMArena result pages, parses each model's detail-page specification tables, and best-effort enriches them from the model-specific comparison page (where GSMArena publishes its “Our Tests” rows). Requests + BeautifulSoup are used with a minimum request delay, retry handling and separate detail/test source URLs.
4. `SpecificationAgent` identifies explicit model mentions where possible and otherwise ranks catalogue documents with a lightweight BM25 retriever. Complete original source rows are retained in the retrieved context so specific hardware-feature questions can be answered.
5. `AgentOrchestrator` sends retrieved evidence to a local Ollama model in `auto`/`ollama` mode. If Ollama is disabled, missing or unavailable, a deterministic response path answers supported intents without inventing missing fields.
6. `ReviewAgent` turns a phone's stored fields into a structured, balanced strengths/considerations review. The review API uses Ollama when available and otherwise labels its response as rule-based.

## Data model

- `phones`: one row per device and its searchable normalized fields, including separate active-use and endurance test metrics.
- `phone_specifications`: one row per source specification, preserving section and label.
- `price_observations`: dated prices, currency and source; no unsupported price is generated by the scraper.
- `chat_sessions` / `chat_messages`: chat history and associated source references.

## Source and quality handling

The initial 12-phone catalogue is labelled `demo_seed` so the UI and API work immediately. It is not presented as a fresh scrape. Run the scraper to replace a model record with the full set of values found on its GSMArena detail page; the record then carries `data_quality=scraped`, the detail source URL and scrape timestamp; when available it also stores the comparison-page URL for measured test data. Prices are left empty unless a separately verified price observation is added.

## Retrieval and multi-agent choices

The project uses a small BM25 implementation to avoid requiring a hosted embedding API or a heavyweight vector database for a 10–15-device catalogue. The agents are ordinary Python components with focused responsibilities and an explicit orchestrator, keeping the workflow testable without binding a small assessment project to a fast-changing agent framework. The local LLM integration uses Ollama's `/api/chat` endpoint and receives only retrieved database evidence as its factual context.
